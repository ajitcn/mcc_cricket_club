## Inventory rules and snapshot

- This is a snapshot of files and project records in the current checkout, not a client acceptance record.
- `docs/SRS-original.md` is absent. `docs/SRS.md` and `docs/REQUIREMENTS-TRACEABILITY.md` are controlled working evidence, not approved client replacement requirements.
- The status vocabulary below describes only the evidenced scope. A module may contain complete slices and blocked or incomplete slices at the same time.
- Existing approved decisions remain as recorded in `docs/DECISIONS.md`. Code presence, test presence, and historical test results do not create approval.
- No tests were run while preparing this inventory. Test paths show that tests exist; results are historical only when a cited project record reports them.
- No application code, tests, database, or existing documents were changed as part of the inspection. This inventory is a new document.
- The checkout contains 21 directories under `app/Modules`, 26 unit-test files, 1 feature-test file, and 38 database-test files at this snapshot. This is a file count, not a test pass count. Some legacy DB tests are explicitly excluded from the persistent test database by `docs/TEST-DATASET.md` because of destructive cleanup behavior.

### Status meanings

| Status | Meaning |
|---|---|
| `COMPLETE` | A bounded, approved scope has current implementation and recorded focused test evidence; no known in-scope item remains. This is not production release approval. |
| `PARTIALLY_COMPLETE` | The current implementation covers a meaningful approved or foundational slice, with documented gaps or unverified evidence. |
| `NEEDS_VERIFICATION` | Code or test evidence exists, but current behavior, coverage, deployment, or conflicting records need inspection before completion can be claimed. |
| `BLOCKED_BY_DECISION` | Code may exist, but a client/business decision is needed before the affected behavior can be accepted or extended. |
| `OUT_OF_SCOPE` | Current records explicitly defer or exclude the capability from the current scope. Re-entry requires an approved scope change.

## Reconciliation checklist after client response

### 1. Protect and baseline

- [ ] Keep a copy of this inventory and the current traceability, decision, and status documents with the approved baseline record.
- [ ] Record the client response packet and approval evidence without overwriting historical documents.
- [ ] Map each accepted capability to an approved requirement ID and named owner.
- [ ] Mark capability disposition: complete, partially complete, needs verification, blocked by decision, or out of scope.

### 2. Reconcile scope and decisions

- [ ] Update the requirements baseline version/effective date and requirement traceability from client-approved wording only.
- [ ] Preserve existing approved decisions unless the client explicitly supersedes them; record the supersession link and approval details.
- [ ] Keep unanswered decisions `NEEDS_DECISION`; do not infer decisions from implementation, tests, or historical tables.
- [ ] Resolve the conflicts listed above by client confirmation and update status records with dated rationale.
- [ ] Mark historical status and test claims with their original date and scope; do not represent them as current results.

### 3. Reconcile architecture and shared foundations

- [ ] Approve and document the architecture boundary and existing modules to retain in `docs/ARCHITECTURE.md`.
- [ ] Approve the RBAC and branch-scope matrix; map every protected route, record, report/export, and document download to it.
- [ ] Inspect current authentication, branch isolation, private storage, audit protection, and deployment evidence for specific gaps; preserve code absent an approved change request.
- [ ] Document approved schema and data ownership in `docs/DATABASE.md`; do not create migrations solely to match assumptions.
- [ ] Document the approved roles, permissions, branch semantics, and authorization test matrix in `docs/RBAC.md`.

### 4. Prioritize remaining work

- [ ] Build the remaining-work list only from client-accepted scope.
- [ ] Order each item by client priority, security impact, dependencies, and estimated effort; name a responsible owner and release target.
- [ ] Treat unresolved dashboard KPIs, HPP, attendance calculations, document visibility, and RBAC decisions as blocked until approved.
- [ ] Separate implementation fixes from verification/deployment evidence work so existing functionality is not rewritten to satisfy an evidence gap.

### 5. Finish in small slices

- [ ] For each approved item, write acceptance criteria tied to requirement/decision IDs.
- [ ] Identify affected code, data migration, authorization, branch boundary, privacy impact, and dependencies before changing it.
- [ ] Make the smallest focused change; preserve unrelated existing modules and user data.
- [ ] Add/update focused tests for business rules, authorization, branch isolation, validation, workflow and persistence.
- [ ] Run only approved safe tests after verifying environment and dataset; capture command, database/environment, result, and limitations.
- [ ] Review security and duplicate logic; update traceability and current status with evidence links.
- [ ] Track completion against client-approved scope and keep deployment evidence separate from local test evidence.

## Suggested first release-planning output

After the client returns the approval packet, produce a short backlog with one row per accepted remaining item: priority, accepted requirement/decision IDs, current status, concrete gap, dependencies, security impact, effort, acceptance criteria, test evidence required, owner, and target release. Start with verified shared-foundation gaps, then finish approved business slices in dependency order. Do not assign implementation work to unresolved or out-of-scope capabilities.
