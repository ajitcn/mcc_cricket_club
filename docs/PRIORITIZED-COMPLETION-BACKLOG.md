**Purpose:** Finish and verify existing MCC work while preserving the current implementation. This is a proposed sequencing document, not client approval or authorization to change application code.

## Planning constraints

- The project’s approximate 80% completion estimate is a planning assumption, not a measured acceptance result.
- `docs/SRS-original.md` is missing. `docs/SRS.md` and the traceability record are working evidence, not an approved replacement baseline. The client approval packet must be approved before final scope or release acceptance is closed.
- Existing approved decisions in `docs/DECISIONS.md` remain the implementation authority for their recorded scope. Do not infer additional scope from code, test files, historical status tables, or proposed options.
- The statuses below distinguish work that can proceed under recorded approvals from work that must wait for client decisions. For a bounded verified slice, “complete” does not mean production release readiness.
- No tests were run while preparing this backlog. Suggested test commands/evidence are future backlog work and must follow `docs/PROJECT-RULES.md` and `docs/TEST-DATASET.md`; destructive legacy DB suites must not be run against the persistent test database.
- Preserve existing modules and data. If verification exposes a defect, record a focused issue and link it to the approved requirement/decision before changing code.

## Prioritization method

P0 items reduce shared security or release-evidence risk. P1 items close verification gaps in approved core workflows. P2 items reconcile baseline and status records after client response. These rankings do not change client priority or decision status.

## Conflicts that affect sequencing

1. **Missing requirements baseline:** `SRS-original.md` is absent and the replacement packet is not approved. Approved slices can be verified against existing decisions, but final acceptance and remaining-scope priority require client baseline approval.
2. **RBAC status:** `IMPLEMENTATION-GATE.md` says no unresolved RBAC/branch policy decision is identified, while `REQUIREMENTS-TRACEABILITY.md`, `MODULE-STATUS.md`, `AGENTS.md`, and the approval packet identify the final permission matrix as unresolved. Therefore the backlog permits evidence mapping but blocks full access certification and new grants.
3. **Attendance:** `DECISIONS.md` records AT-01–AT-05 approved and AT-06 deferred, while `REQUIREMENTS.md` marks REQ-ATT-001 `NEEDS_DECISION` and `PHASE-1-DECISIONS.md` calls the attendance package unresolved. Split the approved source-event slice from denominator and derived behavior; client confirmation is required for the conflict and any new calculation scope.
4. **Scheduling:** `DECISIONS.md` records SCH-01–SCH-05 approved; `PHASE-1-DECISIONS.md` retains unresolved labels. Project rules say approved decisions in `DECISIONS.md` control ambiguous business behavior, so the bounded approved workflow can be verified; client confirmation is still needed before cleaning up the conflicting status record.
5. **Audit:** `OPS-01` is approved in `DECISIONS.md`, but grouped with unresolved operations in the phase sheet. Proceed with approved audit evidence; do not treat OPS-02/10/11/12 as approved.
6. **Data migration:** `DAT-02` has an `APPROVED` status label but no chosen option and unresolved approval fields; other records list it unresolved. Migration backlog work remains blocked.
7. **Trials:** `TRIAL-01` has an approved contract and REQ-TRIAL-001 is marked implemented, but stale open-question wording remains. Verify against the contract and reconcile wording without widening scope.
8. **Historical implementation claims:** Older readiness rows say some capabilities have no code while the current tree contains code/services/tests. Treat these as dated status conflicts; neither code presence nor old test counts establish client acceptance.
9. **Advanced scope:** `REQ-ADV-001` is later/`NEEDS_DECISION` while modules/test files exist for some advanced capabilities. Existing implementation can be preserved and inventoried; extending or accepting those workflows waits for explicit scope and decisions.

## Definition of backlog closure

The completion backlog is ready to become an implementation/release plan only when:

- The client approves the versioned replacement baseline and records each capability’s acceptance/change/rejection/discussion disposition.
- Conflicting decision/status entries are either resolved by the client or explicitly retained with their limitations and owners.
- Every unblocked task has an approved requirement/decision, bounded acceptance criteria, owner, dependency, and evidence environment.
- Every blocked item remains out of development until the relevant decision is recorded.
- Completion evidence distinguishes code review, automated tests, production/deployment checks, and client acceptance.
